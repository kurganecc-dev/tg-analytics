# TG Analytics — сервис разбора Telegram-каналов

Превращает выгрузку канала (`.jsonl`) в аналитический отчёт: охваты и вовлечённость,
динамика, ритм публикаций, темы, анатомия текста и связи постов. Всё считается
в браузере — данные никуда не отправляются.

## Быстрый старт

```bash
cd ~/Desktop/Hermes/test/tg-analytics

# основной способ: сервер отдаёт страницу И качает каналы по ссылке
python3 scripts/serve.py                  # → http://127.0.0.1:8000
# в интерфейсе вставьте https://t.me/имя_канала, укажите месяцы и нажмите «Загрузить канал»
# 12–24 месяца — это десятки страниц t.me: обычно 1–3 минуты, в интерфейсе идёт счётчик времени

# с телефона или другого компьютера в той же сети:
python3 scripts/serve.py --host 0.0.0.0   # напечатает и адрес в локальной сети

# вариант 2: ссылка из командной строки (без браузера)
python3 scripts/fetch_channel.py https://t.me/имя_канала --months 12
python3 scripts/fetch_channel.py @имя_канала --months 6 --max-posts 120 --build

# своя выгрузка .jsonl — подойдёт любой из способов запуска
python3 scripts/build_report.py ~/Desktop/Hermes/test/etagi-copy/corpus/nedvij_etagi.jsonl --name nedvij_etagi
python3 -m http.server 8000               # → http://localhost:8000/ (только просмотр, ссылки не работают)
```

**Глубина истории.** Поле «за N мес.» — основной ограничитель: скрипт листает превью назад, пока не дойдёт
до границы периода, и подрезает лишнее, если страница заехала дальше. Потолок по числу постов выключен
(`--max-posts 0`), аварийный предел — 600 страниц. Замеры на реальных каналах: `nedvij_etagi --months 12` → 699 постов
(2025-10-13 → 2026-10-19); `ipotekapro --months 24` → 630 постов (2024-10-19 → 2026-10-17), то есть ровно запрошенный
период. Медиа-посты без текста в отчёт не попадают, но их число показывается в сообщении («пропущено N постов без текста»).

**Важно:** `python3 -m http.server` — это просто раздача файлов, в нём нет `/api/channel`, поэтому загрузка
по ссылке недоступна (кнопка станет «Только через serve.py»). Для ссылок нужен `serve.py` — он отдаёт и страницу,
и API. Приложение проверяет это само запросом `/api/health` и честно объясняет, что доступно на текущем адресе.

Четвёртый путь — перетащить `.jsonl` прямо в открытую страницу (или нажать «Выбрать файл»).
Можно несколько файлов и каналов сразу: появится вкладка сравнения.

Второй путь без сервера вообще — одним файлом:

```bash
python3 scripts/build_report.py --embed --out report.html выгрузка.jsonl
open report.html          # автономный HTML со вшитыми данными
```

## Загрузка по ссылке: что можно и чего нельзя

Работает через публичное веб-превью Telegram (`t.me/s/<канал>`) — без авторизации, токенов и API-ключей.

| Поле | Как получается |
|---|---|
| дата публикации | точно, из атрибута `datetime` |
| просмотры | точные целые числа (у очень крупных каналов Telegram округляет до «1.2K») |
| реакции | точная сумма по реакциям |
| текст | с эмодзи и переносами; ссылки `t.me/…` сохраняются (для графа связей) |
| ссылка на пост | формируется как `https://t.me/<канал>/<id>` |

Ограничения, о которых нужно знать:

- только **публичные** каналы: закрытые, «по инвайту» (`t.me/+hash`) и каналы с отключённым веб-превью не отдаются;
- посты-медиа без подписи пропускаются (в отчёте видно, сколько таких);
- просмотры — **живые** на момент загрузки: у старых постов они выше, чем в архивной выгрузке;
- история доступна на всю глубину, но качается страницами по ~20 постов, поэтому есть `--months` и `--max-posts`;
- разметка текста чуть отличается от экспорта Telegram Desktop (порядок переносов и подписи ссылок),
  на метрики и стилометрию это не влияет.

Сверка с архивной выгрузкой `nedvij_etagi` за один и тот же период (45 постов за 3 месяца):
даты совпали 45/45, реакции 45/45, просмотры 35/45 — расхождения только из-за роста просмотров
после даты выгрузки.

## Формат входа

JSONL, одна запись на пост:

```json
{"channel":"nedvij_etagi","post_id":3385,"text":"…","date":"2026-10-16T14:02:00+00:00","views":1234,"reactions":12,"url":"https://t.me/nedvij_etagi/3385"}
```

Обязательны `post_id`, `text`, `date`. Лишние поля игнорируются, битые строки считаются и не ломают отчёт.

**Токены `erid`** при сборке заменяются на `[REDACTED]` — значения в отчёте не сохраняются.

## Что показывает

| Раздел | Содержимое |
|---|---|
| **Обзор** | KPI (посты, медиана/среднее/P90 просмотров, реакции, ER по просмотрам, ER на пост, виральность, доля топ-10 % в просмотрах; после ввода подписчиков — ER по подписчикам, охват поста, просмотров на подписчика), медиана просмотров по месяцам, распределение просмотров, просмотры × реакции, топ-10 постов, выбросы (≥3× медианы), тишина (посты без просмотров) |
| **Динамика** | публикации по месяцам, вовлечённость по месяцам (ER, реакции на пост), недельная динамика, срез по годам |
| **Ритм** | тепловые карты «день недели × час UTC» по числу постов и по медиане просмотров, лучшие слоты, загрузка по дням недели |
| **Темы** | доли тем, медиана просмотров по темам, таблица с ER и трендом (доля темы в последние 6 месяцев против предыдущей истории), топ-пост темы |
| **Анатомия и стиль** | длина поста и фразы, эмодзи, типы зачинов, системы разметки списков, призывы к действию, частые финальные строки, дисциплина текста: каждая строка раскрывается в список постов с этим отступлением (нарушение подсвечено, клик по элементу — карточка поста) |
| **Связи постов** | граф связей (дубли, ссылки внутри канала, тематические серии), группы дублей и почти-дублей, внешние каналы из ссылок и @упоминаний, ссылки пост → пост, тематические цепочки-рубрики, рекламные размещения |
| **Все посты** | поиск по тексту, фильтр по теме и просмотрам, сортировка по дате/просмотрам/ER/реакциям, постранично, карточка поста по клику |
| **Методика** | определения всех метрик и ограничения данных |

Кнопки: **Экспорт JSON** (все агрегаты), **Печать / PDF** (светлая печатная тема), **Другой канал**.

## Дисциплина текста: раскрываемый список

Строки в таблице «Дисциплина текста» кликабельны: раскрывается список постов, где правило нарушено —
с датой, просмотрами, реакциями, темой и подсвеченным фрагментом нарушения. Первые 12 постов показаны сразу,
дальше кнопка «Показать все N». Клик по элементу списка открывает карточку поста с полным текстом.

Проверяемые правила: «Этажи» в кавычках и без них, «риелтор»/«риэлтор», хэштеги, прямые кавычки,
двойные пробелы, латиница внутри кириллицы, процент через пробел, фразы длиннее 32 слов, хайп-лексика,
канцелярит, обещания и гарантии.

Правила сформулированы так, чтобы не считать лишнего: из бренд-проверки исключены подпись канала
(«Этажи | NewsRoom», «Подписывайтесь на Этажи NewsRoom»), хэштеги вида `#этажи_новости`, любые кавычки
и этажность («до 5 этажей»). Без этих исключений счётчик «Этажи без кавычек» завышается в четыре раза
(175 вместо 43 постов).

## Подписчики и ER по аудитории

В шапке есть поле **«Подписчиков»**. Пока оно пустое, вовлечённость считается только по просмотрам
(ERR = реакции/просмотры). После ввода числа появляются:

- **ER по подписчикам** = реакции на пост / подписчики × 100 % (медиана и среднее);
- **Охват поста** = медиана просмотров / подписчики × 100 % (плюс средний и P90);
- **Просмотров на подписчика** за весь период и реакций на подписчика за всю историю.

Число запоминается в браузере по имени канала (localStorage), подставляется в сравнительную таблицу каналов,
экспорт JSON и печать. Если заполнить число при сборке отчёта — оно уже будет в файле:

```bash
python3 scripts/build_report.py выгрузка.jsonl --name канал --subs 12000
python3 scripts/build_report.py --embed --out report.html выгрузка.jsonl --subs 12000
```

Контроль ошибок ввода: если медиана просмотров превышает 300 % от подписчиков или охват меньше 5 %,
поле подсвечивается предупреждением — обычно это значит, что число введено не то.

Важно: подписчики в выгрузке отсутствуют, а число, которое вы вводите, — снимок на сегодня. Поэтому для
прошлых месяцев охват и ER считаются против текущей цифры: при росте канала это нижняя оценка. Суммировать
реакции за годы и делить на одно число подписчиков нельзя — корректная метрика считается на пост.

## Запустить для себя: GitHub Pages

Сервис — статика: ни сборки, ни зависимостей, ни сервера. Проверено публикацией в подпуть с не-локального хоста
(как `username.github.io/репозиторий/`): данные подхватываются, все 11 разделов работают, шрифт и тема на месте,
ошибок JS нет, единственный пропавший ресурс был favicon (теперь иконка встроена).

**Что работает без бэкенда**

- весь анализ, графики, скоринг черновика, план, A/B по дате, one-pager, сравнение каналов — всё считается в браузере;
- загрузка собственных выгрузок файлом (перетаскиванием) — целиком на клиенте;
- автозагрузка подготовленного `data/report-data.json` при открытии страницы;
- оформление Windows XP, печать в PDF, экспорт JSON.

**Что без сервера не работает — и почему**

| функция | причина |
|---|---|
| «Загрузить канал по ссылке» | браузер не может запросить `t.me/s/канал`: у Telegram нет CORS-заголовков, запрос блокируется |
| «Замеры скорости набора» | пишутся в файлы на диске (`data/snapshots/`), статике писать некуда |

Обе функции на опубликованной странице не пытаются стучаться в несуществующий API, а показывают объяснение:
кнопка меняется на «Только локально», раздел замеров пишет, что он доступен при локальном запуске.

**Как получать свежие данные без бэкенда**: расписание в GitHub Actions.

В репозитории лежат два файла:

- `channels.txt` — какие каналы обновлять: `<имя> <месяцев истории> [подписчиков]`;
- `.github/workflows/refresh-data.yml` — ежедневно (05:17 UTC) скачивает каналы, пересобирает
  `data/report-data.json` и `report.html` и коммитит изменения. Зависимостей нет: `fetch_channel.py` работает
  на стандартной библиотеке. Запуск вручную — Actions → «Обновить данные каналов» → Run workflow.

Так сервис остаётся статическим, а данные обновляются раз в сутки. Если нужна загрузка по ссылке вживую —
это уже сервер: `serve.py` на любой машине/VPS или serverless-функция с тем же `/api/channel`.

**Куда публиковать** (важно из-за приватности данных):

| вариант | приватность | цена |
|---|---|---|
| GitHub Pages, публичный репозиторий | **все посты и тексты видны всем** | бесплатно |
| GitHub Pages, приватный репозиторий | данные закрыты | нужен GitHub Pro |
| Cloudflare Pages / Netlify, приватный репозиторий | данные закрыты | бесплатно |
| GitHub Pages без данных в репозитории | закрыто: данные грузятся файлом вручную | бесплатно |

Тексты постов в отчётах очищаются от рекламных токенов `erid` (заменяются на `[REDACTED]`), но сами посты
остаются текстами канала. Если в выгрузках есть клиентские каналы — публичный репозиторий не подходит.

**Пошагово (публичный репозиторий)**

```bash
cd ~/Desktop/Hermes/test/tg-analytics
git init && git add index.html assets data report.html channels.txt .github .nojekyll
git commit -m "TG Analytics: сервис анализа каналов"
git branch -M main
git remote add origin https://github.com/<логин>/<репозиторий>.git
git push -u origin main
```

Затем Settings → Pages → Source: Deploy from a branch, ветка `main`, папка `/ (root)`.
Сайт будет на `https://<логин>.github.io/<репозиторий>/`. Файл `.nojekyll` в корне отключает обработку Jekyll.

## Оформление: Windows XP (по умолчанию)

Интерфейс собран как окно Windows XP: заголовок с кнопками, строка меню, панель задач с «Пуском», строка состояния.
Токены взяты не «по мотивам», а сняты с сайта-референса (durevpn.com) через computed styles:

| что | значение |
|---|---|
| поверхность | `#C3C3C3`, светлая фаска `#F0F0F0`, тёмная `#262626` |
| акцент | тёмно-синий `#02007F`, зелёный акцент `#00FF00`, предупреждение `#D45033` |
| фаски | `inset -2px -2px 0 #262626, inset 2px 2px 0 #F0F0F0` — как у референса |
| шрифт | Monocraft (пиксельный), сабсет с кириллицей 13,7 КБ, лицензия OFL 1.1 |
| графики | белое поле, классическая палитра Windows/Excel 97 (navy, teal, olive, maroon) |

Что живёт в оболочке:

- **Окно** — свернуть / развернуть / закрыть (кнопка на панели задач возвращает окно). Развёрнутое окно занимает
  экран за вычетом панели задач, высота содержимого рассчитана так, чтобы страница не прокручивалась.
- **Меню** — Файл, Вид (11 разделов + оформление), Данные, Справка. Команды нажимают те же кнопки, что были раньше,
  поэтому аналитика не зависит от оформления.
- **Пуск** — быстрый доступ к разделам и загрузке данных, в трее часы.
- **Строка состояния** — канал, число постов, период.
- **Переключение оформления** — кнопка «🎨 тёмное / Windows XP» в шапке сервиса, она видна в любой теме
  (горячая клавиша Ctrl+Shift+T, а в XP ещё Вид → Оформление и пункт в «Пуске»). Выбор запоминается в localStorage.

  Почему переключатель стоит именно в шапке: в XP-теме всё оформление заперто под `[data-theme="xp"]`, и вместе с ним
  в тёмной теме скрывается оболочка окна — строка меню, панель задач, «Пуск». Тумблер внутри оболочки оказался бы
  недоступен ровно в том состоянии, из которого нужно вернуться. Поэтому он живёт в нейтральном месте (шапка сервиса),
  а сама тёмная тема не изменилась.

Печать one-pager работает в обеих темах: в XP-обёртке правило «скрыть прямых детей `body`» спрятало бы и сам отчёт,
поэтому обёртка возвращается, а лишние разделы скрываются адресно. Проверено настоящим `Page.printToPDF`:
**ровно 1 страница, 1198 знаков текста**.

Файлы: `assets/xp.css` (тема), `assets/xp.js` (окно, меню, панель задач), `assets/fonts/monocraft-subset.woff2`.

## Сравнение каналов (вкладка «Сравнение каналов»)

Работает, когда загружено два и более канала (по ссылке или файлами). Вкладка считает при открытии.

- **Кого с чем** — выбор каналов A и B чипами, кнопка «добавить канал по ссылке» рядом.
- **Главное отличие от обычной таблицы** — переключатель «сравнивать только по общему периоду».
  С полной историей 1663 поста за 6 лет против 118 постов за 2 месяца сравниваются разные эпохи;
  с выравниванием остаётся пересечение дат (в примере 2026-05-08 → 2026-10-16, 342 × 118 постов).
- **Профили каналов** — медиана, постов в неделю, ER, реакции на пост, виральность; охват и ER по подписчикам,
  если число подписчиков введено для канала.
- **Лицом к лицу** — 11 показателей с проверкой значимости: для числовых — U-критерий Манна—Уитни
  и размер эффекта Клиффа, для долей — z-тест двух пропорций. Вывод различает «A лучше», «B лучше»,
  «различие мало» (p < 0.05, но эффект < 0.1) и «не доказано» (данных не хватает).
  Для длины поста и числа эмодзи вердикт нейтральный — «A больше» / «B больше»: больше не значит лучше.
- **Распределение** — «ящик с усами» (P25–P75 и P10–P90) плюс таблица перцентилей с отношением A/B.
- **Динамика** — медиана по месяцам обоих каналов, с режимом «в процентах от первого месяца»,
  чтобы сравнивать форму кривой, а не масштаб.
- **Темы** — доля и охват каждой темы в обоих каналах; «лучше своего обычного» показывает,
  какие темы канал умеет, независимо от размера аудитории.
- **Стиль и качество** — длина, эмодзи, «ёлочки», источники, призывы, внешние ссылки, хайп, читабельность Flesch.
- **Рейтинг** — все загруженные каналы по выбранному показателю, место, отставание от лидера, период.

Честность сравнения обеспечена тремя вещами: выравниванием периода, интервалами/значимостью вместо голых процентов
и требованием минимального размера эффекта. Проверка расчётов A/B — отдельным скриптом:

```bash
python3 scripts/verify_compete.py corpus_A.jsonl corpus_B.jsonl
# сверяет общий период, профили, U-критерий, z-тесты долей и перцентили с движком
```

## Что делать (вкладка «Что делать»)

Четыре блока, которые превращают отчёт в решение. Все считаются в браузере, сеть не нужна.

### Скоринг черновика
Вставьте текст — система оценит вероятность, что пост соберёт больше, чем типичный для текущих месяцев,
покажет, какие признаки тянут вверх и вниз, и прогонит 14 правил стиля «Этажей».

- **Цель — «выше типичного для этих же месяцев»**: для каждого поста берётся медиана соседей в окне ±45 дней.
  По всей истории цель ломается о падение просмотров по годам (медиана 2021 — 2120, 2026 — 926): модель начинала
  предсказывать календарь, а самым «сильным» признаком оказывалось время суток. После перехода на локальную медиану
  AUC вырос с 0.553 до 0.61, а признаки стали осмысленными.
- **Качество показывается честно**: AUC на 5 последовательных временных блоках (случайное разбиение завысило бы
  оценку — соседние посты коррелируют). Для `nedvij_etagi` — AUC 0.61, то есть модель различает лучше монетки,
  но это подсказка, а не прогноз. Интерфейс прямо пишет уровень: «различает слабо».
- **Форма учитывает контекст дня**: сколько постов выйдет в тот же день. Это самый сильный признак модели
  («постов в тот же день» −0.57) — публикация нескольких постов в сутки размывает просмотры.
- **Чек-лист стиля отделён от вероятности**: правила не влияют на балл модели, и наоборот — вероятность не оправдывает
  нарушение правил, о чём интерфейс предупреждает, если провалено больше трети пунктов.

Проверка расчёта: `python3 scripts/verify_scoring.py выгрузка.jsonl` — та же модель на Python, совпадение до
0.00e+00 по вероятностям черновиков из `tests/score-fixtures.json`.

### A/B по дате
Выберите дату и окно (по умолчанию 90 дней) — метрики «до» и «после» с теми же тестами, что в сравнении каналов.
Так проверяется вмешательство: смена формата, рубрики, тона. Вердикт отделяет доказанное изменение от разброса.

### План на неделю
Слоты «день недели × час» по историческим медианам с интервалами 95 %, по одному посту на день, лучшая рубрика слота.

- **Ожидание пересчитывается в масштаб текущего канала**: множитель = медиана последних 60 дней / медиана за всю
  историю (для `nedvij_etagi` — 0.46). Без этого план обещал бы охват эпохи 2021 года.
- Слоты с пометкой «как везде» преимущества не доказали — это «ждать как обычно», а не приглашение публиковаться.
- Время показывается в UTC и МСК.

### One-pager для руководства
Кнопка собирает одну страницу: KPI, пять ключевых выводов, «что делать» (слоты, рубрики, признаки, дубли, план)
и сразу открывает печать — сохраняется в PDF. Печатью управляет класс `print-exec`: печатается только сводка.

## Глубокий анализ (вкладка «Глубокий анализ»)

Считается при первом открытии вкладки (≈1 с на истории 1663 поста), в браузере, без сервера.

**Что даёт сверх обычных метрик**

| Блок | Что показывает | Как считается |
|---|---|---|
| Выводы | 10–13 формулировок с числами: динамика, слоты, драйверы, рубрики, дубли, стиль | правила по посчитанным метрикам, каждое со ссылкой на значение |
| Интервалы | медиана и среднее с 95 % доверительным интервалом | бутстрэп, 600 ресемплов |
| Тренд | изменение медианы в % за месяц с интервалом и R² | OLS по логарифму медианы месяца |
| Точки перелома | где динамика меняла уровень и на сколько | бинарная сегментация по медианам (L1) |
| Драйверы | какие признаки текста и формата связаны с просмотрами: медианы «с/без», размер эффекта, значимость | U-критерий Манна—Уитни с поправкой на связи, размер эффекта Клиффа |
| Слоты | день × час с интервалами; «выше среднего» — только если интервал слота целиком выше интервала канала | бутстрэп по каждому слоту |
| Эффект соседства | влияние интервала между постами, переноса охвата с предыдущего поста, плотных дней | значения очищены от тренда (отношение к медиане ±15 дней), U-критерий, Спирмен |
| Рубрики | охват и вовлечённость 13 форматов (дайджест, карточки, аналитика, розыгрыш…) со значимостью | шаблон текста + U-критерий + интервалы |
| Читабельность | индекс Flesch для русского, длина фраз, доля длинных, пассив, «мы», клише, канцелярит | Оборнева-адаптация Flesch, слоги по гласным |
| Дрейф стиля | как менялись длина, эмодзи, кавычки, источники, вопросы по годам | по годам публикаций |
| Прогноз | медиана просмотров на 3 месяца с интервалом | тренд по лог-медиане + сезонность месяца (если ≥3 лет истории) |
| Бенчмарк | место канала в пуле: перцентиль по 9 показателям | пул в браузере, экспорт/импорт JSON |
| Аномалии | всплески охвата, охват без реакций, служебные записи | z по медиане и MAD (> 3.5) |
| Скорость набора | просмотров в сутки, прирост за замер, когда рост прекращается, время насыщения τ | сравнение замеров `snapshot.py` |

**Что проверено, а не заявлено**

Числа движка сверены с независимой реализацией тех же алгоритмов на Python
(`scripts/verify_deep.py`, `scripts/node_harness.js` — прогон в Node без браузера):

```bash
python3 scripts/verify_deep.py corpus.jsonl     # «всё совпало» или список расхождений
```

Совпадают до знака: бутстрэп-интервалы, U-критерий и Клифф, тренд, точки перелома, драйверы, слоты,
рубрики, качество текста, прогноз, эффект соседства. Для этого PRNG (mulberry32) реализован
одинаково в JS и Python, а проверка гоняется на двух разных каналах.

**Чего в анализе нет и почему**

- Подписчики не выводятся из данных — их вводит человек (см. раздел выше), иначе ER по аудитории был бы выдуман.
- Скорость просмотров нельзя достать из одной выгрузки: нужны замеры. Скрипт `snapshot.py` копит снимки,
  `growth.py` считает по ним скорость и насыщение; реальный пример — `data/snapshots/nedvij_etagi.jsonl`
  (2 замера: выгрузка 16.10 и живой замер через 2 часа): 10 из 62 постов росли, медиана 28 просмотров в сутки
  у растущих, рост прекращается примерно к 3.5 суток. τ не оценивается, пока растущих постов меньше 10 —
  модель на насыщенных постах не идентифицируется.
- Причинность не утверждается: критерии показывают связь и её устойчивость, а не «эмодзи увеличивает охват».

## Метрики: как считаем

- **ER по просмотрам (ERR)** = реакции / просмотры × 100 % — качество контента без опоры на размер аудитории.
  **ER по подписчикам** = реакции на пост / подписчики × 100 % — для сравнения каналов разного размера
  (появляется после ввода числа подписчиков).
- **Виральность** = P90 просмотров / медиана: во сколько раз топ-10 % постов обгоняют обычный пост.
- **Темы** — ключевые слова с приоритетами (первое совпадение побеждает), один пост = одна тема.
- **Дубли** — совпадение первых 10 слов и близость по Жаккару ≥ 0,7.
- **Цепочка темы** — посты одной темы подряд с интервалом ≤ 10 дней.
- **Ограничения**: просмотры и реакции — снимок на момент выгрузки (скорость набора просмотров
  по такому файлу не считается); время публикации — UTC; служебные посты («Channel photo updated»)
  остаются в данных и занижают метрики.
